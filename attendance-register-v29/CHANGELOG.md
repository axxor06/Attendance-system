## v28.2 fair rate limiting, seed semester-count fix, and orphaned-script cleanup

Fixed a real fairness bug found while tracing why normal UI use could plausibly trigger 429s: the general API rate limiter (`app.use('/api', generalLimiter)`, 300 requests/15 min) was keyed by IP address alone. On any deployment where multiple real users share one public IP — a campus NAT gateway, a shared lab, a mobile carrier's CGNAT — all of their traffic counted against the same bucket, so one busy user's requests could throttle a completely unrelated person. Every other endpoint-specific limiter in the file (password-change, QR generate/scan, attendance-submit, message-send) already keyed by authenticated user with an IP fallback for pre-login requests; `generalLimiter` was the one place that pattern hadn't been applied. Fixed by adding `keyType: 'user'`, reusing the existing `keyGenerator` logic rather than writing new keying behavior. Verified: syntax-checked, full server suite re-run clean (unaffected, since no test asserted the old IP-only behavior).

Fixed the seed script's disagreement with the live application over department semester counts. `Department.programLevel`/`semesterCount` already existed in the schema, and `classController.js`/`ClassesPage.jsx` already correctly derive each department's valid semester range from them (defaulting diploma to 6, everything else to 8) — a real HOD can already create a 6-semester department through the actual Academic Management screen today. `seed.js`, however, hardcoded `programLevel: 'degree', semesterCount: 8` for every department it creates and looped class generation `semNumber <= 8` unconditionally, never consulting the field at all. Added a shared `effectiveSemesterCount(dept)` helper matching the exact fallback already proven correct in the live controller/page, and used it in `ensureDepartments` (persist the definition's real values), `ensureClasses` (loop to the department's own count), the capstone-subject label (last semester of *that* department, not a hardcoded 8), and `ensureSemesters` (size the shared global semester pool to the longest configured program rather than a bare 8). This makes the demo data generator capable of mixed-length programs; it does not by itself add the diploma department names from an earlier message, since which departments to seed is still an open decision — this only fixes the mechanism. Verified: syntax-checked, and a new test (`security.test.js`) statically pins the helper's use in all three functions and the absence of the old hardcoded `<= 8`/`semesterCount: 8` literals.

During a debug-artifact/dead-code sweep of the codebase (no TODOs/FIXMEs, no hardcoded secrets, no deprecated Mongoose/CommonJS patterns found; all `console.*` calls are either CLI-tool output, requestID-correlated best-effort-failure logging, or explicitly gated behind `DEBUG_TIMETABLE_CONFLICTS`/`import.meta.env.DEV`), found one genuinely orphaned file: `seed_government_polytechnic.js` — a complete, working alternate seed for a single real institution (6 named departments, 6 semesters) — had no `npm run` entry, unlike every other utility script in the project. Added `"seed:polytechnic"` to `server/package.json` and a corresponding note in `README.md` so it's discoverable rather than something you'd only find by browsing the file tree. Confirmed it runs and fails cleanly on the expected "MONGO_URI is required" with no database configured; a full live run against MongoDB remains a staging-environment check, same as the rest of this project's OTP/email/DB-dependent flows.

Also corrected an unrelated self-inflicted mistake mid-session: an edit meant to insert a new test accidentally deleted an adjacent test's opening declaration line, orphaning its body and breaking `security.test.js`'s syntax. Caught immediately by re-running the suite (not by assuming the edit was clean), fixed, and re-verified. Noting it here in the interest of the same no-false-claims standard applied to the rest of this project.

Server: 81/81 tests passing (80 prior + 1 new). Client: 28/28 tests passing, 0 lint warnings, clean build. Both dependency audits: 0 vulnerabilities.

## v28.1 email-change verification and dependency refresh

Fixed a real gap found during a full-codebase audit: `PATCH /auth/me` allowed any authenticated Student, Faculty, or HOD account to change its own login email and marked it verified instantly, with no proof of ownership of the new address and no notice to the old one. This mattered because email is the account's password-recovery channel — a briefly hijacked session could have silently redirected it. Email changes now go through a verify-before-apply flow: `POST /auth/me/email-change` stores the target as `pendingEmail`, emails an OTP to the new address using the existing OTP infrastructure, and immediately emails the current address to alert the real owner even before confirmation. `POST /auth/me/email-change/confirm` applies the change only after the OTP is verified and re-checks uniqueness for the verification-window race; `POST /auth/me/email-change/cancel` clears a pending request. All three sit behind `protect` and reuse the existing `otpGenerateLimiter`/`otpVerifyLimiter`. The general profile-update endpoint no longer accepts `email` at all. The ProfilePage UI was rebuilt around this flow using the existing `OtpInput` component so it matches the verification UX already used for registration and password reset, and now surfaces a pending change in the read-only account view, not just mid-edit.

Applied dependency updates that stay within each package's existing semver range and were verified with a clean install afterward: `mongoose` (server) and `axios`, `framer-motion`, `lucide-react`, `react`, `react-dom`, `recharts`, `tailwindcss`, `vite`, `@vitejs/plugin-react`, `@types/react`, and `@types/react-dom` (client). `oxlint`'s in-range update was evaluated and deliberately reverted after it silently enabled a new default rule category (React Compiler advisory lints) that produced 58 warnings across pre-existing files in an app that does not use React Compiler; taking a lint tool's newer default behavior was judged riskier than the version bump was worth, so it stays pinned to the version that keeps the verified zero-warning baseline. Express, Mongoose (major), Helmet, express-rate-limit, dotenv, bcryptjs, rate-limit-redis, and framer-motion's next major were left untouched as available-but-deferred major-version upgrades, each a breaking-change surface outside this round's scope. `imagekit` remains on its deprecated package name (`@imagekit/nodejs` is the maintained successor); migrating it is a package swap, not a version bump, and needs live ImageKit credentials to verify, so it's recorded here rather than attempted blind.

Added `tests/server/emailChange.test.js` covering the new flow with the same no-live-database methodology the rest of the suite uses: the OTP-purpose enum and schema accept `email_change` and reject unknown purposes, `pendingEmail` normalizes case/whitespace and stays `select: false`, all three new routes require authentication before any database access, the general profile endpoint's contract no longer includes `email`, both new routes carry the correct rate limiters, and the controller source is asserted to write `email` only after OTP verification and to notify the old address at request time. The existing `uiContracts.test.js` assertion tied to the old direct-write payload was updated to match the new contract instead of being deleted. Server: 80/80 tests passing (72 prior + 8 new). Client: 28/28 tests passing, 0 lint warnings, clean production build. Both dependency audits report 0 vulnerabilities after a clean-room `npm ci`.

As with prior rounds, this was verified statically and via the existing non-live test harness; a live round trip of the new OTP email against a running MongoDB/SMTP pair remains a staging-environment check, consistent with every other OTP-based flow in this project.

## Combined timetable conflict remediation

The timetable conflict path now distinguishes the two sources of conflicts. The PUT path derives the active timetable document from the route’s class ID, normalizes its actual Mongo `_id`, and excludes that document and current class from external conflict queries without trusting a browser-supplied exclusion.
