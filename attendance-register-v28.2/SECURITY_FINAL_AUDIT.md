# Final Security Audit

## Scope and rating method

This audit covers the current Attendance Register v28.1 source after the availability investigation, reliability remediation, v24 Faculty attendance-period correction, v25 directory/timetable UI polish, v26 messaging/profile/responsive polish, v26.1 server-filtered recipient-tab and Faculty-period fixes, v27 registration, message-action, dashboard, and search polish, v27.1 end-to-end security hardening, v28 sidebar/Messages/theme refresh, and the v28.1 operational hardening pass. The assessment distinguishes implementation evidence from live-system evidence. A checklist item is not considered verified merely because a route or document exists. Any workflow that requires MongoDB, Redis, SMTP, ImageKit, multiple devices, concurrent requests, or a deployed HTTPS origin is marked **UNVERIFIED** when it could not be exercised in this sandbox.

> **Honest assessment:** the source has strong defensive controls and passed the available static, unit, contract, syntax, lint, build, dependency, OpenAPI, and mock-backed browser gates. A production score of 10/10 cannot be claimed until the live staging scenarios in `PRODUCTION_CHECKLIST.md` are executed.

## Availability and save-path root-cause finding

The prior availability defect was in the shared conflict-detail helper: the availability path passes a hypothetical requested slot containing order and time but no Faculty, while the helper checked `slot.faculty` before examining persisted candidates. The corrected logic compares each persisted `candidate.faculty` with the supplied candidate `facultyId` and uses the hypothetical slot only for day/time overlap. Break and free slots remain non-blocking. The route distinction remains explicit: `/api/timetables/:classId` receives a class ID, while `data.timetable._id` is the separate persisted timetable-document ID. Availability resolves the active timetable from the selected class, rejects a mismatched `excludeTimetableId`, validates exact raw slot membership, and excludes the resolved document directly from external checks.

The PUT path resolves the active timetable from the class route, normalizes its actual `_id` to a Mongo ObjectId, and excludes that exact document plus the current class from the external query. It does not trust a frontend exclusion for save security. The complete submitted weekly payload is analyzed separately: same-day overlapping assignments for one Faculty become `internalConflicts`; overlapping assignments found in other timetable documents become `externalConflicts`. Development diagnostics record both counts, first examples, exact ranges, Faculty IDs, slot IDs, conflicting timetable/class IDs, and whether a conflict matches the active timetable. Existing internal duplicate validation and genuine cross-class conflicts remain HTTP 409 checks.

The client now accepts Axios request configuration, sends the selected subject, uses a per-request `AbortController`, tracks request identity, ignores stale results, and models each class slot as `idle`, `loading`, `success`, `empty`, `error`, or cancelled/stale. The paired class-timetable and subject-list load uses the same cancellation scope; changing class clears old state and stale responses cannot overwrite the current timetable. Availability sends only validated IDs from that same current timetable state. A final cleanup path converts any current request that unexpectedly remains loading into a retryable error rather than leaving an infinite spinner. Academic Management uses bounded requests for every subject page, preserving the server’s global pagination limit while preventing false zero counts. The selector therefore transitions to a real Faculty list, an explicit empty state with counts, or a precise error.

## Raw slot identity and subject-count remediation

The source-level defect in the Smart Seed was that it built embedded slot object literals and wrote them through the native MongoDB collection API without explicit `_id` fields. Because the schema’s Mongoose subdocument defaults are not applied by that native write, raw persisted timetable documents could lack nested slot IDs even though a normal Mongoose response appeared to contain an identifier. Availability intentionally validates `slotId` membership against the raw current timetable, so this mismatch can produce the observed HTTP 400 stale-slot message. This diagnosis is strongly supported by the write path and controller contract, but it is **not claimed as live-proven** until raw seeded Mongo documents are inspected.

The v22 source fix assigns a deterministic Mongo ObjectId derived from class/day/order to every generated class, break, and free-period slot before `updateOne`, reads the raw documents back, validates unique IDs and overlap totals, and refuses Smart Seed completion on any failure. `validate:timetables` prints `Missing slot IDs: N` and exits nonzero for missing, invalid, or duplicate IDs. `diagnose:timetable-ids` prints raw nested IDs by day for staging proof. Academic Management no longer filters only the default first subject page: it requests bounded pages of 100 records (the server maximum), merges all pages, and uses the complete set for class badges and expanded lists. The regular paginated subject endpoint and its server-side authorization remain unchanged.

## Authentication persistence finding

A frontend restart can legitimately preserve the authenticated session because the browser retains the valid HTTP-only refresh cookie. The access token is held in memory and is not stored in localStorage or sessionStorage. The client uses a single-flight refresh coordinator and StrictMode-safe bootstrap protection. Server-side refresh rotation, reuse detection, family revocation, logout, token-version invalidation, account deactivation, password reset, and password change remain enforced. This behavior is not evidence that security was lowered.

## v24 Faculty attendance-period root-cause finding

The Faculty “No periods for this subject” symptom came from a broader subject discovery scope than exact timetable ownership. A subject can list several qualified Faculty members in `subject.faculty`, while the actual day/period owner is stored on the timetable slot. The Faculty page could therefore offer a subject that had no slot for that Faculty on the selected class day, after which exact server filtering correctly returned no period. Earlier request-order issues could also leave a stale deep-link period selected before class periods finished loading.

The correction narrows Faculty subject discovery, dashboard subjects, and pending-attendance links to exact active timetable ownership, while retaining a controlled legacy-template fallback. The period endpoint now validates `classId`/`subjectId` and returns only matching persisted class-timetable slots for the authenticated Faculty; both manual and QR selectors retain a client-side exact subject/Faculty check, wait for a matching period before requesting a roster or generating QR, and cancel stale requests. A shared single-flight helper prevents duplicate identical reads during StrictMode. The backend `resolveSessionContext` exact subject/class/date/period/Faculty checks remain enforced and continue to reject forged requests with HTTP 403.

## v25 directory and timetable UI polish

The HOD Faculty directory now starts with an All Departments view and exposes a department dropdown only for the Faculty-managed route. A selected department is sent as the existing validated `department` query to the protected paginated `/api/users` endpoint. Search and pagination remain server-backed, summaries reflect the selected result set, and Student directory behavior is unchanged.

The timetable editor now presents day tabs as compact cards with visible slot counts, separates slot identity from editable scheduling fields, groups type/subject/Faculty controls apart from time/note controls, and uses responsive spacing and card hierarchy to reduce congestion. No request shape, persisted timetable ID, nested slot ID, availability state machine, conflict response, or authoritative save check was changed.

## v28.1 operational hardening

The follow-up pass was intentionally targeted rather than a checklist-driven rewrite. The Node HTTP server now bounds request, header, keep-alive, and shutdown lifetimes through documented environment controls with production-range validation. Express returns safe actionable responses for malformed JSON, oversized bodies, unexpected multipart files, and common database duplicate fields without exposing database values. Access logs are compact structured records containing request ID, method, route path, status, duration, and response size; API and activity-log failure logs are metadata-only. Response compression is enabled for payloads above 1 KB, and a restrictive Permissions-Policy disables unused browser capabilities. Client refresh failures are epoch-aware so concurrent terminal failures cannot invalidate a newer session, and Messages conversation polling pauses while the page is hidden and resumes on visibility. HOD-managed reset credentials are temporary, bounded by `ADMIN_RESET_PASSWORD_TTL_MS`, rejected after expiry, and server-gated to the authenticated change-password endpoint until completion.

No refresh rotation, reuse detection, relationship authorization, text-only messaging rule, attendance/QR guard, timetable conflict check, database model, or existing navigation item was removed or weakened.

## Browser verification

An isolated mock-backed browser run exercised the actual timetable page at the requested route. A delayed success response transitioned from `Checking availability…` to a real Faculty list and displayed `2 Faculty available` with two Faculty options. A delayed empty response transitioned to `No Faculty available for this period` and reported that all two eligible Faculty were assigned. A delayed 503 response transitioned to `Availability unavailable` with a precise retry instruction. The error panel includes the conflicting class when the server returns it, and the current slot can be highlighted from the returned day/order/time details. These checks prove the client lifecycle and rendering behavior, but they are not live MongoDB or production authentication evidence.
